[SECTION 1: VERSION OVERVIEW & VISUAL ARCHITECTURE DIAGRAMS]
--------------------------------------------------------------------------------
Version 4 evolves the MiniCommerce platform to support Asynchronous Background Task
Processing (ARQ + Redis), Redis-backed Sliding-Window Rate Limiting Middleware,
Customer Storefront Real-Time Decoupling Features, and a Secured Admin Observability
Dashboard featuring an OpenTelemetry-Style Waterfall Distributed Trace Visualizer.

Architectural Overview:
1. HTTP Checkout Requests are strictly focused on atomic PostgreSQL transactions
   (SELECT FOR UPDATE, stock deduction, order insertion, cart clearing, db.commit()).
2. All non-critical side effects (receipt generation, low-stock threshold audits,
   analytics metrics) are offloaded to an async ARQ background worker pool post-commit.
3. API endpoints are protected by Redis Sorted Set sliding-window rate limiting.
4. Admin routes (/api/v1/admin/* and /admin UI) are secured via JWT admin roles.

[SECTION 2: NEW TECHNOLOGIES & CORE CODE SNIPPETS]
================================================================================

1. ARQ Asynchronous Queue Integration (`app/worker.py`):
```python
from arq.connections import RedisSettings
from app.core.config import settings
from app.tasks.order_tasks import send_receipt_email, audit_low_stock, record_analytics_event

class WorkerSettings:
    functions = [send_receipt_email, audit_low_stock, record_analytics_event]
    redis_settings = RedisSettings.from_dsn(settings.REDIS_URL)
    max_tries = settings.TASK_MAX_RETRIES
```

2. Redis Sliding-Window Rate Limiting Middleware (`app/middleware/rate_limiter.py`):
```python
window_seconds = 60
now = time.time()
clear_before = now - window_seconds
key = f"rate_limit:{client_id}:{tier_name}"

pipe = redis.pipeline()
pipe.zremrangebyscore(key, 0, clear_before)
pipe.zadd(key, {f"{now}": now})
pipe.zcard(key)
pipe.expire(key, window_seconds + 5)
results = await pipe.execute()
```

3. Post-Commit Task Offloading (`app/services/order_service.py`):
```python
await db.commit()
arq_pool = get_arq_pool()
if arq_pool:
    await arq_pool.enqueue_job("send_receipt_email", str(order.id), user_email, str(total_amount), _job_id=f"email_{order.id}")
    await arq_pool.enqueue_job("audit_low_stock", product_audit_list, _job_id=f"stock_{order.id}")
```

[SECTION 6: ERROR LOG & RESOLUTION TRACKER]
================================================================================

1. Error: ResponseValidationError on `updated_at` field in `ProductResponse`
   Symptom: HTTP 500 Internal Server Error on `GET /api/v1/products` catalog requests.
   Root Cause: `ProductResponse` defined `updated_at: datetime` as required/non-nullable, but Supabase PostgreSQL catalog records contained `null` values for `updated_at`.
   Solution: Updated `app/schemas/product.py` to set `created_at: datetime | None = None` and `updated_at: datetime | None = None`. Updated Redis catalog serialization in `app/services/product_service.py`.

2. Error: UndefinedColumnError: column users.is_admin does not exist
   Symptom: HTTP 500 Internal Server Error during `/auth/login` and `/auth/register`.
   Root Cause: `Base.metadata.create_all` creates missing tables but does NOT add new columns to existing PostgreSQL tables created in V1-V3.
   Solution: Executed `ALTER TABLE users ADD COLUMN IF NOT EXISTS is_admin BOOLEAN NOT NULL DEFAULT FALSE;` in migration script `app/db/migrate_idempotency.py` and added automatic column migration execution to FastAPI's `lifespan` handler in `app/main.py`.

3. Error: Admin Observability Gate remains locked for pre-existing Admin accounts
   Symptom: Logging in as `admin@minicommerce.com` returned `is_admin: false`, preventing access to the Admin Dashboard.
   Root Cause: Pre-existing user rows created prior to V4 received `is_admin = FALSE` when the column was added. `seed.py` skipped existing user records without updating properties.
   Solution: Executed `UPDATE users SET is_admin = TRUE WHERE email = 'admin@minicommerce.com';` via `app/db/promote_admin.py` and updated `app/db/seed.py` to refresh `is_admin` flags for existing seed users.

4. Error: `AdminDashboard.jsx` login form re-renders post-login
   Symptom: Clicking "Authenticate as Admin" in UI authenticated backend session, but view did not unlock Admin Dashboard.
   Root Cause: `/auth/login` returns `{ access_token: "..." }` without a nested user object, leaving `res.data.user` as `undefined` until `/auth/me` is called.
   Solution: Updated `handleAdminLogin` in `AdminDashboard.jsx` to execute `GET /auth/me` after `/auth/login` and store full `userProfile`. Added automatic token validation on component mount.

5. Error: Benchmark script `run_benchmarks.py` using simulated `time.sleep()` calls
   Symptom: V4 async checkout benchmark baseline relied on hardcoded `time.sleep()` delays.
   Root Cause: Baseline comparison needed a synchronous model representation after `OrderService` was refactored for ARQ async.
   Solution: Refactored `run_v4_async_checkout_benchmarks` to run real task functions inline vs ARQ Redis job enqueuing for 100% empirical zero-sleep execution measurements.

6. Error: Docker Container static asset caching & hot reloading delay
   Symptom: Backend code edits did not reflect in running container, and Nginx served cached compiled Vite JS bundles.
   Root Cause: Missing volume mounts for `./backend` in `docker-compose.yml`, and Nginx serving compiled static assets from Docker build stage.
   Solution: Added `volumes: - ./backend:/app` in `docker-compose.yml` for instant backend hot-reloading and documented `docker-compose up --build` for frontend asset compilation.

7. Error: Vite Dev Proxy `ECONNREFUSED 127.0.0.1:8000` on initial launch
   Symptom: Vite terminal outputs `[vite] http proxy error: /api/v1/admin/metrics Error: connect ECONNREFUSED 127.0.0.1:8000`.
   Root Cause: Vite dev server initializes in ~1.6s and immediately starts polling backend telemetry endpoints before Uvicorn completes its database lifespan initialization on port 8000.
   Solution: Once Uvicorn finishes binding to port 8000 (after ~2s), all proxy requests succeed automatically. For production, Docker Compose handles startup ordering via container healthchecks.
